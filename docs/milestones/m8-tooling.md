# M8: Tooling

The tools that let someone who is not the engine's author make content for it.

**Status:** Planned.

## Charter

- A map editor writing the native formats directly: terrain sculpting, texture layer painting, object
  placement, player slots, waypoints.
- Live validation in the editor: the same cross-checks the package loader performs, surfaced while
  editing rather than at load.
- Package building: assemble a map package, with the scenario stored uncompressed so it stays diffable
  inside the archive.
- An asset pipeline: validate and import glTF models, report what an asset uses that the renderer does
  not yet support.
- A command-line inspector for every native format, so a broken file can be diagnosed without the
  editor.
- A machine-authoring pack: everything a language model needs to produce a complete scenario on
  demand — terrain, placements, scripts — and to check its own work. Specified in
  [Machine authoring](#machine-authoring) below, because it is more than documentation.

## Exit condition

A map authored entirely in the editor, by someone who has not read the format specifications, loads and
plays. And its machine counterpart: a scenario generated by an agent given only the machine-authoring
pack — terrain recipe, placements, script — validates, loads, and renders.

## Design notes

The editor writes the same formats the engine reads, with no intermediate project format. This costs
some editor convenience and buys something worth more: there is no export step to diverge, and a map
that opens in the editor is a map the engine can load by construction.

Validation is shared code with the package loader, not a reimplementation. Two validators drift, and
the one in the editor is the one that would drift toward permissiveness.

The command-line inspector exists because the editor will eventually fail to open something. A format
whose only reader is a GUI is a format nobody can debug.

## Machine authoring

The pack exists so an agent can produce a decent scenario on demand, which takes four things beyond
format documentation:

- **A terrain recipe.** `.cict` is bulk binary that no language model can emit and no diff can
  review. The recipe is its text-native complement: base elevation, placed features — a hill, a
  ridge, a plateau, a river as a spline, a ramp between heights — layer painting as named regions,
  and seeded noise, compiled deterministically to the container. The same recipe produces the same
  bytes, so a recipe is testable the way a scenario is. The editor's sculpting stays the human path;
  the recipe is the generated, reviewable one, and a base pass a human can take into the editor too.
- **A catalog command.** What may be referenced is the mounted content's business, not a document's
  to hand-maintain: the command reads the actual mounts and emits, machine-readably, the template
  identifiers with their kinds and models, the models present, the terrain layer names the renderer
  resolves, the string keys, and the script surface — host verbs and events with arities. A
  generator can then only cite what exists, and the list cannot drift because it is derived.
- **Spatial queries.** Accurate placement needs ground truth: world extent, height and slope at a
  point, and — once M6 defines it — passability. The same numbers let validation refuse a placement
  on a cliff face rather than only one outside the map, which the package cross-check already
  catches.
- **A closed loop with eyes.** Validation proves well-formed, not good. The headless scenario render
  the engine already has is the pack's final tool: generate, validate, render, look at the image. An
  agent that cannot see its terrain will ship a plausible heightfield that plays like a parking lot.

The delivery vehicle is an agent skill wrapping the pack and these commands, not a plugin into a
content tool: the commands are the same ones a human uses at the shell, which keeps one validator and
one writer per format.

## Explicitly not done

- No model or animation authoring. glTF was chosen precisely so existing content tools do that job.
- No in-editor scripting. It follows a scripting layer existing at all.
- No asset store or mod distribution. The resource layer's mount ordering already supports mods being
  installed; distributing them is not an engine problem.
